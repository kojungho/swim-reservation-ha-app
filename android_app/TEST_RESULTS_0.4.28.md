# Android 0.4.28 (34) / addon 2.15.33

- Includes 0.4.27/2.15.32 fixed-bank-payment support. While that artifact was being prepared, user requested adaptive telephone/mandatory terms and private entered-value records; these additions are delivered together in 0.4.28/2.15.33. Failed November 1 plan is not re-executed.
- Exact known field names/IDs take precedence; unambiguous aliases/associated labels/aria-label/placeholder can identify personal fields. Korean 10/11-digit mobile numbers are formatted as digits, hyphens, spaces, or three recognized segments/select-prefix and then compared numerically to the requested number and checked against browser constraints. Names/payers remain distinct. Missing/ambiguous/disabled/read-only controls, incompatible formats and overlapping mappings stop before submission. This is bounded compatibility, not a guarantee for arbitrary future forms or country-code changes.
- Mandatory refund/booking/privacy checkboxes can be identified without the old class. Optional/advertising/marketing/master-consent/third-party or unknown mandatory consent is not silently accepted. Already selected optional consent also blocks submission. Form verification reuses the same read-only resolver immediately before final submit; it does not repair changed values. Hidden payment and CSRF fields remain unmodified.
- Capture-only mode returns successful personal form fields after validation: original name, raw formatted/split phone fields plus normalized lookup phone, payer, request and arrival. This mode is not passed into trace logs. It excludes tokens, cookies, whole HTML and unknown fields. The snapshot is the verified pre-click DOM/FormData, not a claim that later server-side/on-submit transformations cannot occur.
- New private reservation submission record is written before a possible submit, initially check_required; only a validated completion receipt changes it to complete with reservation number/amount/status. Failed validation before submit creates no record. Existing unknown-submit/no-retry protections remain. Entry values are immutable after creation, independent of later saved-profile edits. Deleted records are not resurrected by late completion. UI title is 예약 제출 정보 under 예약자 정보, with lookup using the captured identity and record-only deletion; no cancellation endpoint is used.
- Addon storage: permission 0600, atomic file, root/shared queue across independent plan/parallel child stores. Android: separate AES-GCM/Keystore document, synchronized across run slots, not part of public HA display settings. Existing profiles/plans/drafts are not migrated or deleted. Maximum 200 records; full/erroring storage blocks a new submission rather than losing its entry. Receipt-state update failure after verified success retains the pre-submit record, reports failure to update the record, and never resubmits.
- Tests: 38 server DOM/engine/record/static/parallel/privacy tests passed, plus 7 app/addon UI tests covering captured-identity lookup, record-only deletion, keyboard/scroll regressions and stage flow. Payment resolver body and submitted-records UI are byte-identical between surfaces. Mock submits only; no real booking/cancel/payment or live identity lookup.
- JVM 52 tests passed including encrypted immutable records, no active run side effects and record-only delete.
